[`bootstrap_id_protocol_sim.py`](../tools/bootstrap_id_protocol_sim.py) is the toy/ASCII routing model which provides the logic for some `generate_..._json.py` files.

We often use the Builder class defined in [`generate_bootstrap_chip_id_readback_json.py`](../tools/generate_bootstrap_chip_id_readback_json.py), which takes the desired network size plus a source-chip coordinate `(source_x, source_y)` and provides the steps needed to assign a chip ID to every chip. The protocol is built from sequential configuration writes that set chip IDs and enable specific TX lanes. It can also describe a configuration read after assigning a chip ID. These Builder-derived steps are the starting point for both the startup-driven and RTL-preconfigured flows.

In the startup-driven flow we first decide the network size, source coordinate, and one or more target chips that should later emit event traffic. A script such as [`generate_bootstrap_event_startup_json.py`](../tools/generate_bootstrap_event_startup_json.py) or [`generate_bootstrap_chip_id_readback_json.py`](../tools/generate_bootstrap_chip_id_readback_json.py) writes a human-readable startup JSON in this directory. That startup JSON is then compiled by [`compile_startup_json.py`](../tools/compile_startup_json.py) into a `*.compiled.json` file containing tick-stamped UART frames ready for the live orchestrator.

In the RTL-preconfigured flow we still use the same Builder logic, but instead of transmitting the bootstrap packets at runtime we derive the final steady-state register values and preload them directly into each RTL chip before tick `0`. The helper for this is [`generate_bootstrap_preconfigured_event_init_json.py`](../tools/generate_bootstrap_preconfigured_event_init_json.py). Its output is an `init_...json` file containing final `CHIP_ID`, `ENABLE_PISO_UP`, and `ENABLE_PISO_DOWN` values plus per-target channel-enable and unmask writes. Some scenarios patch this init JSON further to override downstream masks or other target-local settings before launch.

After the network topology and target chips are fixed we generate a stimulus JSON describing the analog charge injections. This file usually contains one `charges[]` entry per injected channel with a `runtime_id`, `tick`, `channel`, and `charge`. For startup-driven event runs the stimulus tick is often shifted to land after the last startup frame. For staggered or multi-target runs the stimulus JSON simply contains a larger list of per-chip injections at different ticks.

The run scripts in [`sim_core/scenarios`](../scenarios) then build the required binaries, choose a working directory under `build/`, and launch the generated `build/orchestrator_larpix` executable with either `-startup_json` or `-init_regs_json`, plus `-stimulus_json`, `-trace_out`, and optional occupancy/debug capture arguments. The orchestrator runs the live chip grid, emits a `trace.jsonl`, writes `run.log`, and for some scenarios also writes occupancy CSV or chip-internal debug CSV sidecars.

Once the live run completes we convert `trace.jsonl` into browser playback JSON using [`convert_live_trace_to_playback.py`](../visualizers/packet_transmission/convert_live_trace_to_playback.py). This is the maintained converter for bootstrap, configuration, and event scenarios. The playback JSON records `initial_chips`, packet spans, chip events, FPGA events, and optional `run_summary` metrics. The run scripts typically print both `playback_json=...` and a `visualizer_url_hint=...` line at the end.

The final visualization step is to serve `chip_network_sim/` locally and open [`sim_core/visualizers/packet_transmission/index.html`](../visualizers/packet_transmission/index.html) with a `?playback=...` query pointing at the generated playback JSON. If a scenario also produced `chip0_rx_debug.csv` and that CSV is referenced by the playback JSON, the visualizer can show the `Chip 0 View`; otherwise it stays in network view only. This is the full workflow from network idea, to generated config/init/stimulus files, to live run artifacts in `build/`, to a replayable browser visualization.

## Note on runtime logging

The orchestrator is intentionally not responsible for collecting rich per-tick chip state. Its main job is to drive lock-step control with `TICK` and `DONE`, launch the child processes, and optionally launch the trace collector. The richer event stream used by the visualizer goes from each chip process to [`trace_collector_larpix`](../src/trace_collector_larpix.c), which writes `trace.jsonl` from trace events such as packet transmit, packet receive, charge injection, and shared FIFO occupancy changes.

The CSV side logs such as FIFO occupancy captures or `chip0_rx_debug.csv` are a separate path again. Those are not sent over an `nng` socket to the orchestrator or trace collector. Instead they are written directly inside the relevant chip process during the live tick loop, which is why they can reflect bit-accurate or tick-accurate local state from that chip rather than only the higher-level event summaries recorded in `trace.jsonl`.
